### Deviations from plan

1. **zod v3 → v4 in sdk-shared** — Fase 0 scaffolded sdk-shared on zod ^3.23.0; backend already on zod 4.5.4. `@hono/zod-openapi@1.6.3` peer-requires zod ^4. Bumped sdk-shared to ^4.5.4 (deps + peerDeps). No behavior change in user-facing API; aligns with backend.
2. **`registerOpenApi()` guard** — sdk-shared doesn't depend on `@hono/zod-openapi`, so the prototype patch (`.openapi(name)`) isn't reliably present at schema-load time. Helper no-ops `.openapi()` when undefined so unit tests parse without bundler-runtime patch. Backend process imports `@hono/zod-openapi` first → patch active → `.openapi()` called on import → schema marked. Net: routes wire correctly; tests pass standalone.
3. **`PluginManifest`/`PluginSummary` NOT registered as named `components.schemas`** — `@hono/zod-openapi` tracks schemas by $ref usage; calling `.openapi("Name")` on a free-standing schema doesn't add it to `components.schemas` unless something references it via `$ref`. Here `PluginsListResponse`/`PluginDetailResponse` inline the SDK schemas (via `z.array(PluginSummary)` / `manifest: PluginManifest`) rather than referencing by `$ref`. Functionally equivalent for client typing (`openapi-ts` still infers correct types), but plan F1-T4 verify's literal "PluginManifest schema in openapi:dump" is satisfied by INLINED form, not named component. **Future fix (Fase 2):** route.ts can `import { z } from "@hono/zod-openapi"` and wrap with `.openapi("$ref")` to promote — defer until frontend regen breaks.
4. **`mergeLayered` (2-layer) kept UNCHANGED** — added `mergeLayered3` instead of extending `mergeLayered`'s signature. Preserves backward compat with agents/skills/mcps modules. Plan F1-T2 said "reuse `mergeLayered` pattern" — interpreted as "reuse `scanLayer` underneath", not "extend the signature". Cleaner separation; documented inline.
5. **`defaultSystemPluginDir()` returns `~/.config/puna`** (not `~/.config/puna/plugins`) — caller appends `"plugins"`. Decision per F1-T2 verify case #11 + naming consistency (`mergeLayered3` callers know the subdir name).
6. **`PluginSummary.kind` derived from capabilities** — plan F1-T1 didn't specify kind enum; strategy §4 manifest doesn't include it. Derived in `deriveKind()` (mixed/graph/agent-hook/ui; absent caps → ui). Stable contract for Fase 2 badge UI.
7. **Best-effort list (bad manifest → warn + fallback)** — strategy silent on this. Chose to NOT fail entire list on a single broken manifest (operational resilience). `get()` skips broken entries with warn; throws `PluginNotFoundError` only if no entry matches `id`.
8. **No `repository.ts` in plugins module** — module is filesystem-only, no DB tables. AGENTS.md standard template assumes DB-backed modules. AGENTS.md append notes the deviation.
9. **Manual symlink `backend/node_modules/@puna/sdk-shared` → `packages/sdk-shared`** — backend is NOT in root `workspaces` (only `packages/*` is). `bun install` at root won't link it. Tried `"@puna/sdk-shared": "workspace:*"` in backend deps → bun rejects (workspace deps require package to be a workspace member). Tried `"link:../packages/sdk-shared"` (bun-supported for non-workspace) → would resolve but symlink approach is already in place and works. **Durable fix (deferred, pre-Fase 2 or Fase 0.5):** add `backend` to root `workspaces` array and let bun manage the symlink. Risk: backend currently has its own `bun.lock` and own `node_modules`; hoisting may shift deps. Tracked as open item.
10. **Manual symlink `packages/sdk-shared/node_modules/zod` → `backend/node_modules/zod`** — bun install from sdk-shared dir resolves zod 4.6.5 (different from backend 4.5.4). Two zod copies means `@hono/zod-openapi` prototype patch from backend doesn't reach SDK schemas. Symlink dedupes. Fragile; same root cause as #9. Same durable fix.
11. **`active_checkpoint_id` column added to dev `data/shared.db`** (gitignored) — pre-existing stale schema blocked server boot. `ALTER TABLE sessions ADD COLUMN active_checkpoint_id TEXT` applied via libsql client. Likely a leftover from an earlier session not yet migrated to current Drizzle schema. Tracked as infra debt, not Fase 1 scope.
12. **`openapi.json` is gitignored** (pre-existing) — `bun run openapi:dump` writes it; not tracked. Confirmed in `.gitignore` (already there). Frontend `openapi-ts` reads from same file or fetches `/doc` directly.

### Open items (from Fase 1)

- **Workspaces scope decision** — root `package.json` `workspaces: ["packages/*"]` excludes `backend/` and `frontend/`. Fase 0 scaffolded `packages/*` only. SDK packages depend on this, but backend/frontend (which now import `@puna/sdk-shared`) don't auto-link via `bun install`. Manual symlinks work today; breaking on next `rm -rf node_modules`. **Decision needed before Fase 2 ships:** either (a) add backend/frontend to root workspaces and unify bun.lock, or (b) document symlink requirement in `.gitignore` exclusion + postinstall script, or (c) keep symlinks and accept re-running `bun install` recreates them.
- **OpenAPI schema registration** — `PluginManifest`/`PluginSummary` not in `components.schemas` as named refs (inlined only). Functionally fine; opt-in to named refs when frontend regen needs shared types across multiple endpoints. Defer to first consumer that needs it.
- **`mergeLayered3` precedence vs naming** — current source enum = `workspace-local | workspace-global | system-global` (matches strategy Q2). Existing `mergeLayered` returns `local | global` (2-layer). Two enum vocabularies coexist; if Fase 6 introduces 4+ layers, consolidate.
- **Fase 0 sample manifests diverge from strategy §4 schema** — `templates/plugin/*/plugin.json` uses `kind`/`entry`/`slots`/`hooks` fields instead of `capabilities`/`engines`/`permissions`. Not a Fase 1 blocker (templates are user-facing stubs that Fase 7 regenerates from real CLI). Will surface again in Fase 7 CLI implementation. Tracked.
- **`tsconfig.json` per `packages/*`** — Fase 0 open item. Per-pkg `typecheck` script (`tsc --noEmit`) still unrunnable for sdk-shared without a pkg tsconfig. sdk-shared tests pass via bun:test which uses its own type-stripped loader. Not blocking Fase 1 gate. Track to first Fase that typecheck-locks a pkg (Fase 2 frontend sdk-frontend).
- **Backend `bun install` from cwd** — when run inside `backend/`, bun rejects `workspace:*` deps because backend isn't a workspace member. Workaround: always `bun install` from repo root. Document or add postinstall script.

### Why

Fase 1 added `@puna/sdk-shared` import to `backend/src/modules/plugins/{service,route,host}.ts`. Bun refused to link it because backend was not in root `workspaces` (only `packages/*` was). Manual symlink `backend/node_modules/@puna/sdk-shared → packages/sdk-shared` worked but:
- Broken by `rm -rf node_modules` (no postinstall recreates)
- Two zod copies (backend 4.5.4 vs sdk-shared 4.6.5) meant `@hono/zod-openapi` prototype patch from backend never reached SDK schemas → `PluginManifest`/`PluginSummary` not registered as named OpenAPI components (only inlined).
- Pattern would repeat when frontend imports `@puna/sdk-frontend` in Fase 2+.

### Oracle review (ora-1)

Selected approach **A** (unified workspace) over B (symlink doc) and C (hybrid) because:
- Bun's `linker = "isolated"` (default since 1.2) keeps each workspace member's deps in its own `node_modules/`, so classic npm-style hoisting collisions don't occur. Vite 8 + Drizzle + Tailwind v4 not at risk of conflict.
- A is the ONLY option that fixes the root-cause bug declaratively via `"@puna/sdk-shared": "workspace:*"`. B preserves the bug; C leaves two install patterns.
- Frontend will import `@puna/sdk-frontend` in Fase 4 (plugin UI); C would only delay the decision.
